# IEP GEN — Dev Plan (MVP รอบส่งใบสมัคร)

เอกสารนี้สำหรับทีม dev 2 คน อ่านให้เข้าใจตรงกันก่อนเริ่มโค้ด

---

## 1. เป้าหมายรอบนี้ — อ่านตรงนี้ก่อนทุกอย่าง

**เราไม่ได้ทำ product ให้สมบูรณ์ เราทำให้ครูการศึกษาพิเศษใช้ทำงานจริงได้ทัน 31 ก.ค.**

เหตุผล: รอบ Bootcamp เราแพ้ทีมที่มี user data จริงแล้ว รอบนี้เราจะมีบ้าง — และ user จริงของเราคือครูที่ต้องทำ IEP จริงสิ้นเดือนนี้พอดี

**สิ่งที่ต้องได้เมื่อจบโปรเจกต์นี้:**
1. ระบบที่ deploy ขึ้นเว็บจริง ครูเปิดใช้จากที่ไหนก็ได้
2. แผน IEP ที่ครูทำเสร็จด้วยระบบเรา (ของจริง ไม่ใช่ demo)
3. ตัวเลขเวลา before/after ที่จับจริง
4. รายการทุกจุดที่ครูแก้ output ของ AI (= insight ที่ทีมอื่นไม่มี)

> **หลักตัดสินใจตลอดโปรเจกต์:** ถ้าฟีเจอร์ไหนไม่ช่วยให้ครูทำ IEP เสร็จเร็วขึ้น → ตัดทิ้ง ไม่ต้องเถียง

---

## 2. Solution คืออะไร (สรุปสั้น)

ครูกรอกข้อมูลเด็กแบบเลือกจากตัวเลือก (dropdown/checklist ไม่ต้องพิมพ์ prompt)
→ ระบบค้นข้อมูลที่ถูกต้องจาก mapping table
→ ส่งให้ LLM เรียบเรียงเป็นภาษาเอกสารราชการ
→ ครูได้เป้าหมาย IEP + รายการสื่อที่เบิกได้ + เหตุผลประกอบ
→ ครู copy ไปวางในระบบ SET ของ สพฐ. เอง

**หลักการสำคัญที่ต้องยึดตอนเขียนโค้ด:**

| ส่วน | ใครตัดสินใจ | เหตุผล |
|---|---|---|
| สื่อ/บัญชี ก-ข ที่แนะนำ | **Mapping table** (rule-based) | ผูกกับงบเบิกจริง ผิดไม่ได้ ห้ามให้ LLM คิดเอง |
| ภาษา/การเรียบเรียง | **LLM** (few-shot) | ต้องการภาษาราชการที่ลื่นไหล |
| การยืนยันขั้นสุดท้าย | **ครู** | ระบบไม่ auto-submit เข้าระบบราชการเด็ดขาด |

## 3. MVP Scope — ทำแค่นี้ ห้ามเกิน

### ✅ ต้องมี (Must have)

- [ ] หน้ากรอกโปรไฟล์เด็ก — **เฉพาะประเภทความพิการที่ครูต้องใช้จริงสิ้นเดือนนี้** (ยังไม่ต้องครบ 9 ประเภท)
- [ ] Generate เป้าหมาย IEP — เสนอ 2-3 ตัวเลือกให้ครูเลือก
- [ ] Generate รายการสื่อ/บัญชี ก-ข + เหตุผลประกอบ
- [ ] **ปุ่ม Copy ข้อความ** ทุกช่อง (ให้ครูวางเข้าระบบ SET ได้ทันที)
- [ ] แก้ไขข้อความที่ AI สร้างได้ (textarea ธรรมดาก็พอ)
- [ ] Deploy ขึ้นเว็บจริง (Vercel)

### ⏸️ ทำถ้าเวลาเหลือ (Nice to have)

- [ ] IIP (วิธีสอน)
- [ ] ปุ่ม Regenerate เมื่อแก้ข้อมูลโปรไฟล์
- [ ] Consistency check พื้นฐาน
- [ ] เพิ่มประเภทความพิการอื่น

### ❌ ไม่ทำรอบนี้ (ตัดทิ้ง)

- ระบบ login / user account
- Database (ใช้ JSON file ใน repo พอ)
- Export PDF/Word สวยงาม
- Dashboard ผู้บริหาร
- เชื่อมต่อ API ระบบ SET จริง
- Mobile responsive แบบสมบูรณ์ (แค่ใช้ได้บนคอมพอ)

## 4. Tech Stack

```
Framework : Next.js (App Router) — frontend + API route ในโปรเจกต์เดียว
Styling   : Tailwind CSS
AI        : Claude API หรือ OpenAI API (เรียกจาก API route ฝั่ง server เท่านั้น)
Data      : JSON file ใน repo (mapping table + few-shot examples)
Deploy    : Vercel (auto deploy จาก main branch)
Repo      : GitHub (private)
```

**ทำไมเลือกแบบนี้:** ไม่ต้องแยก backend server, deploy ได้ใน 5 นาที, ครูเปิดใช้ได้จากทุกที่โดยไม่ต้องติดตั้งอะไร

> ⚠️ **API key ต้องอยู่ฝั่ง server เท่านั้น** (ใน API route) ห้ามใส่ใน client code เด็ดขาด

## 6. แบ่งงาน

### คน A (เจ้าของ domain — คนที่ประสานกับครูการศึกษาพิเศษได้)

**ไฟล์ที่รับผิดชอบ:** `/data/*.json`, `/lib/prompts.ts`, `/app/api/generate/route.ts`

- [ ] คุยกับครูเก็บ requirement (ดูข้อ 7)
- [ ] สร้าง `mappingTable.json` — ระดับความสามารถ → สื่อ/บัญชี ก-ข
- [ ] สร้าง `fewShotExamples.json` — ตัวอย่าง input/output จากแผน IEP จริงของครู (ลบชื่อเด็ก)
- [ ] เขียน system prompt + few-shot prompt
- [ ] เขียน API route: รับ request → lookup mapping table → เรียก LLM → return JSON
- [ ] ทดสอบ output กับครู ปรับ prompt จนครูบอกว่า "ใช้ได้"

### คน B (frontend + infra)

**ไฟล์ที่รับผิดชอบ:** `/app/page.tsx`, `/components/*`, Vercel config

- [ ] ตั้ง repo + Next.js + Tailwind + deploy หน้าเปล่าขึ้น Vercel **ให้เสร็จวันแรก**
- [ ] หน้ากรอกโปรไฟล์เด็ก (dropdown/checklist ตาม schema)
- [ ] หน้าแสดงผล: เป้าหมาย IEP (เลือกได้) + รายการสื่อ + เหตุผล
- [ ] ปุ่ม Copy ทุกช่อง + แก้ไขข้อความได้
- [ ] Loading state ระหว่างรอ AI (สำคัญ — ไม่งั้นครูจะคิดว่าค้าง)
- [ ] Error handling เบื้องต้น (API พัง → แสดงข้อความบอก ไม่ใช่หน้าขาว)

**คน B เริ่มได้ทันทีด้วย mock data** ตาม schema ข้อ 5 ไม่ต้องรอ API เสร็จ

## 7. คำตอบจากครูการศึกษาพิเศษ (ยืนยันแล้ว 23 ก.ค.)

1. **จำนวนเด็ก/ประเภทความพิการ:** 16 คน ครอบคลุม 4 ประเภท — ออทิสติก, LD, บกพร่องทางสติปัญญา, บกพร่องทางภาษาและการสื่อสาร
   → เพิ่ม mapping table ให้ครบ 4 ประเภทแล้ว (2 ประเภทหลังยังไม่ผ่านการตรวจกับครู ต้องยืนยันอีกรอบ)
2. **เวลาที่ใช้ทำ IEP จริง:** **1-2 วันขึ้นไปต่อคน** ถ้าต้องปรับมาตรฐาน/ตัวชี้วัดครบทุกวิชา (ไม่ใช่ครึ่งวันแบบที่เคยประมาณไว้จากเอกสารคู่แข่ง)
   → **ใช้ตัวเลขนี้แทนของเดิมทุกที่ที่พูดถึง time savings** (pitch deck, หน้า /stats)
   → คำนวณ: 16 คน × 1-2 วัน = **16-32 วันทำงาน/ปี** ที่ครูใช้ทำ IEP อย่างเดียว
3. **ระบบ SET:** พิมพ์ทีละช่องเท่านั้น ไม่มีปุ่ม import → ยืนยันว่าปุ่ม Copy คือ design ที่ถูกต้อง
4. **ระบบคูปอง:** แยกจากระบบ SET คนละระบบ → ต้องมีปุ่ม Copy แยก 2 ชุด (เป้าหมาย IEP ไป SET, รายการสื่อไปคูปอง) ห้ามรวมเป็นก้อนเดียว

**ยังรอคำตอบ:**
- ตัวอย่างแผน IEP ที่กรอกจริงแล้ว (ลบชื่อ) — ยังไม่ได้รับไฟล์จริง มีแต่ generic examples อยู่ใน `fewShotExamples.json`
- หัวข้อในแบบฟอร์ม IEP จริงของโรงเรียน (เทียบกับที่เขียนไว้ใน export/route.ts)

## 8. กฎเรื่องข้อมูลเด็ก (ห้ามละเมิด)

ข้อมูลเด็กพิเศษ = ข้อมูลอ่อนไหวของผู้เยาว์ ต้องระวังตั้งแต่บรรทัดแรกของโค้ด

- ❌ **ห้ามเก็บชื่อจริงเด็ก** ในระบบ/log/database ใดๆ — ใช้รหัสแทน (เด็ก A, B, C) ครูจำเองว่าใครคือใคร
- ❌ **ห้ามส่งชื่อ อายุ โรงเรียน ไป LLM API** — ส่งเฉพาะประเภทความพิการ + ระดับความสามารถ
- ❌ **ห้าม commit ข้อมูลเด็กจริงขึ้น GitHub** (รวมถึงใน few-shot examples — ต้องลบชื่อก่อน)
- ✅ ถ่ายหน้าจอ/อัดคลิปได้ แต่ต้องปิดข้อมูลระบุตัวตนทั้งหมด

> จุดนี้กลายเป็นจุดแข็งตอน pitch ด้วย — บอกได้ว่า "เราออกแบบ privacy-by-design ตั้งแต่ prototype แรก เพราะทดสอบกับข้อมูลจริง"

## 11. สิ่งที่ต้องเก็บระหว่างครูใช้งานจริง (อย่าลืม!)

นี่คือของที่จะทำให้ใบสมัครเราแข็งกว่าทีมอื่น — **สำคัญพอๆ กับตัวโค้ด**

1. ⏱️ **จับเวลาจริง** — ก่อนใช้ระบบ vs หลังใช้ระบบ ต่อเด็ก 1 คน
2. 📝 **บันทึกทุกจุดที่ครูแก้ output ของ AI** — ทุกจุดที่แก้ = จุดที่ระบบยังไม่ดีพอ = insight ที่ใช้พูดใน pitch ได้
3. 📸 **ถ่ายหน้าจอ** (ปิดข้อมูลเด็ก) ระหว่างใช้จริง
4. 🎥 **อัดคลิปสั้นตอนครูใช้** ถ้าครูยินยอม — ใช้ในวิดีโอ demo ได้ทรงพลังมาก
5. 💬 **ถามครูหลังใช้เสร็จ:** "จะใช้ต่อไหม" / "จะแนะนำเพื่อนครูไหม" ← คำตอบนี้คือ validation ที่แข็งที่สุด
